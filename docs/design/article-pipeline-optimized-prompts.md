# 公众号成稿：直接依据简报写作的提示词清单

日期：2026-10-21。本文保存 direct-brief-v2 的提示词设计基线。运行时代码已迭代至 `direct-brief-v5`；当前阶段顺序与输入输出以 [成稿运行阶段契约](../../skills/wechat-mp-topic-to-article/references/runtime-stage-contracts.md) 为准，本文不作为当前阶段顺序的权威定义。

依据：[现状提示词清单](../article-pipeline-prompt-inventory.md)与[账号配置](../../account-context.json)。本版替代此前包含大纲生成和独立发布前核对的提案。

**确认的流程**

简报＋事实材料 → 初稿 → 事实与逻辑审稿（含必要修订） → 按字数扩缩写 → 表达精修 → 发布标题。

简报与事实材料是输入。正文主流程依次为初稿、事实与逻辑审稿、按字数扩缩写、表达精修、发布标题；审稿中的必要修订和复核属于审稿阶段。长度在配置范围内时，长度阶段将审稿稿透传为 `07-length-adjusted.md` 并保存长度记录，不调用模型；超出范围时才调用长度提示词。扩缩写后的实质改动只做差异复核，不在长度阶段自动修复；之前未解决的审稿问题仍保留在总门禁中。表达精修始终执行，且只改表达、不承担字数调整；其改动同样只做差异复核。复核门禁决定稿件能否发布，不决定长度调整或表达精修是否执行。取消独立大纲生成，不生成隐藏的大纲产物，也不在后续阶段要求读取或对照大纲。

**目标与提示词组合**

文章适合账号的目标读者，有清楚的论证、具体内容和作者判断。账号定位用于选择视角、技术解释深度和语言；文章具体观点来自已确认简报。写作过程中自行组织章节和段落。

每次调用只使用本阶段的 system prompt，user 消息提供对应材料。完整编排技能、其他阶段规则、运营评分和重复的事实风险清单不再逐层拼入 system prompt。程序负责执行顺序、保存产物、状态与重试；模型负责当前写作或编辑任务。

**共享的读者背景（只作上下文）**

写作、表达精修和标题阶段可使用下列背景，审稿直接读取本篇简报与证据：

```text
主要读者是程序员和技术从业者，兼顾技术管理者与泛科技读者。
他们关注工具解决的实际问题，也关注技术、产品和平台变化对工作与选择的影响。
表达通俗、具体，保留理解问题所需的专业细节。
文章允许有鲜明态度、个人观察和判断，具体角度与立场沿用本篇已确认简报。
```

本篇真正相关的读者影响从简报继承，不要求每篇同时讨论岗位、收入、成本和效率，也不强加选型清单、互动提问或关注口号。账号配置中的内容比例和默认文章框架不转为章节要求。

**输入：简报＋事实材料**

保留简报中已经确定的写作角度、命题、主线、冲突、读者影响、采用的研判与明确舍弃的方向。保留作者已经确认的实践和观察，不重新压缩或重新研判这些内容。

事实材料统一为一份可追溯的记录，保留主张、主体、时间、来源、对应证据和影响含义的必要条件。来源单方说法、争议和作者推断按各自属性记录。材料中可包含有归属的评论区观察，但它只说明某位用户的看法或经历，不能替代对事件事实的核验。

已有材料足以成稿时直接进入 P1。核心事实确有缺口时返回编辑备料，避免用写作补造证据。没有独立“生成大纲”或“重新生成写作简报”的模型调用。

**P1：初稿写作**

任务：直接依据简报与事实材料写成完整文章，自主安排结构。

System prompt：

```text
你是一位面向开发者和技术从业者写作的公众号作者。
请根据已确认简报和事实材料，直接写出完整文章。沿着简报的角度与主线，自行安排章节和段落，让事实、解释和作者判断自然衔接。
开头尽快进入值得讨论的具体事件、细节或问题；正文讲清关键关系，让读者理解判断的依据及其实际含义。
允许明确表达作者态度、感受和评价。事实忠于材料，推断的力度与依据相称，不虚构经历、引语、行为或结果。
来源和必要条件自然写进相关事实句。已经交代清楚的限定不再重复说明，有依据的观点直接表达。
内容讲到哪，结构就展开到哪。合并没有新信息的重复解释，结尾在判断讲清时自然收束。
按本篇长度设置输出完整 Markdown 文章，不附写作过程或规划说明。
```

User 模板：

```text
<reader_context>{{读者背景}}</reader_context>
<brief>{{已确认的写作角度、命题、主线、冲突、读者影响、采用与舍弃方向}}</brief>
<facts>{{事实、来源和必要条件}}</facts>
<author_material>{{已确认作者材料；无则留空}}</author_material>
<length>{{本篇长度设置}}</length>
```

文章类型仅在确有需要时追加一条写法提示：技术深解需要解释机制；行业评论重点展开行为、利益关系和结果；轻松趣闻通过真实细节和反差产生趣味。不得再次注入一整套结构、来源、审稿和结尾要求。

初稿可用事件名作为工作标题，正式发布标题由 P5 根据完成的正文生成。

**P2：事实与逻辑审稿**

任务：判断文章事实与推理是否成立，并检查是否落实简报核心命题。只输出具体问题，不重写文章。

System prompt：

```text
请审核文章中的事实与论证，并核对已确认简报的核心命题是否得到展开。
检查重要事实、数字、引语、来源归属和必要条件是否与证据一致；检查推断是否存在缺失前提、因果跳跃或超出依据的结论。
来源支持某人作出声明，不等于声明内容已经独立证实。有依据的作者评价和个人看法可以明确表达，不因语气鲜明而要求弱化。
每项问题必须定位原文，说明对应证据或具体推理缺口，给出最小修复建议。
证据不足的事实应纠正、删除或准确归因；关键推理不足应补清依据或收窄结论。
只报告影响事实、论证或核心命题的具体问题，不提出泛泛的谨慎建议，也不要求用免责声明代替修正。
```

User 模板：

```text
<brief>{{已确认简报}}</brief>
<evidence>{{唯一事实记录及对应来源证据}}</evidence>
<article>{{初稿}}</article>
```

程序要求结构化输出，示意如下：

```json
{"pass":false,"issues":[{"type":"fact|attribution|reasoning|brief","quote":"原文","basis":"证据编号或具体推理缺口","repair":"最小修法","return_to":"materials|draft"}]}
```

通过时问题列表为空。未出现逐句来源提示不是失败理由，作者价值判断无需伪装成可核验事实。来源、样本、条件等是否需要补充，取决于它们会不会改变文章的事实或结论。

**P2：必要修订（仅审稿发现问题时）**

任务：修复 P2 已定位的问题。

System prompt：

```text
按照审稿清单修订文章，只修改问题所在句段和保持衔接所需的上下文。
事实错误依据材料纠正，推理缺口依据现有材料补清或收窄结论。
保留成立的作者观点和表达力度。不得新增事实，也不把局部问题扩写成全篇风险说明。
未涉及问题的内容保持原样，输出完整修订稿。
```

User 模板：

```text
<article>{{待修订文章}}</article>
<issues>{{审稿问题}}</issues>
<evidence>{{对应证据}}</evidence>
```

修订后复用 P2 核对原问题及受影响内容。缺少关键事实时返回材料准备；整篇论证偏离简报时返回 P1，明确给出偏离原因。返回对象不包含大纲。

**P3：按字数扩缩写（仅超出配置范围时调用模型）**

任务：按项目配置的可见字符数范围调整正文篇幅；在范围内时原样透传，不调用模型。

System prompt：

```text
根据输入中的调整方向、调整幅度和策略扩写或缩写文章。保留核心命题、作者立场和事实准确性；按任务取舍段落、章节和表达方式，不必默认保留原有结构。
当 strategy 为 structural 且 adjustment 为 expand 时，补充与主线相关的次要内容，进一步解释观点背后的原因、机制、影响或读者处境。可以使用具体例子、比喻、对比、排比等写作手法，也可以在已有事实支持下深入展开判断。例子不得伪装成真实事件；不得编造数据、引语、来源或亲历。
当 strategy 为 expressive 且 adjustment 为 expand 时，主要调整现有段落的写法，以例子、比喻、对比、排比或更充分的解释增加少量篇幅；不另起次要章节。表达要增加理解或阅读体验，不得同义反复凑字数。
当 strategy 为 structural 且 adjustment 为 shorten 时，删除次要论点、次要章节、重复背景和不推进主线的内容，保留主旨成立所必需的事实与论据。允许重排或删除小标题、段落，不要求保留所有论证顺序。
当 strategy 为 expressive 且 adjustment 为 shorten 时，优先删减比喻、排比、对比铺陈、过场和重复修饰，把观点及其依据改为直接表达；只有修辞本身承载必要含义时才保留。
扩写时可以基于已有事实深入解释因果、机制和影响，但不能把推断写成已证实事实。缩写时不得删改事实含义、来源归属或作者立场。
根据输入中的 target_visible_chars 调整篇幅，结果必须落在 allowed_range 内。只输出完整 Markdown 文章，不说明调整过程。
```

运行时以调整前正文的可见字数与配置范围计算所需变化量；目标取最近边界内缩进 10–50 字（约为区间跨度的 5%），不再固定瞄准区间中点。需要变化达到 200 个可见字符时选择 structural，优先增删次要内容；低于 200 字时选择 expressive，主要调整写作手法。输入包含读者背景、锁定简报、事实权威记录、当前字数、目标字数、允许范围、变化量、调整方向、策略和正文。每次调整后复核变动段落；仍未达标且输出确有变化时，按剩余差值最多再调整一次。最终长度未达标时，交付字数门禁失败，终稿保留待审核状态。

**P4：表达精修**

任务：改善阅读连贯性、删去冗余、保留作者声音。替代分开的去 AI、风格审查与风格返修。

System prompt：

```text
请把文章编辑得清楚、自然、连贯。
删除没有增加信息的重复判断、过场和自我免责句，合并重复段落；保留有推进作用的回扣。
保留有效细节、修辞、作者态度和论证过程。遇到抽象空话，用文章已有的具体内容说清；没有支撑时删去，不编造解释。
调整句长与衔接，让段落顺着内容推进，不按固定句式或词表判断 AI 腔。
保持事实、来源、数值、适用条件和判断含义准确。来源已经说明归属时，不再附加同义声明。
只做表达处理，不承担扩写或缩写任务；不要新增或删除实质内容，精修前后可见字符数尽量接近。
结尾在话说完时结束。输出完整正文，无需修改时返回原文，不附编辑说明。
```

User 模板：

```text
<reader_context>{{读者背景}}</reader_context>
<article>{{按字数处理后的正文}}</article>
```

不追加全篇事实风险清单，也不同时设置“删除重复”与“禁止合并、禁止调整结尾”等冲突规则。若精修实质改变主张范围、来源归属或推理关系，复用 P2 核对受影响内容；不默认对全文再跑一轮综合审稿。

**P5：发布标题**

任务：根据完成的正文生成候选，选定一个适合公众号发布的标题。

System prompt：

```text
为这篇公众号文章生成 5 个发布标题，并推荐其中一个。
从正文最有分量的事实、冲突或判断寻找点击理由，让目标读者一眼看懂文章在讨论什么。
保留必要的事件或主体名称，陌生专名可搭配白话含义。候选从不同角度表达，不只替换同义词。
标题可以有鲜明观点，但承诺必须由正文兑现，不新增未经支持的数字、因果、行为或结果。
对照正文核对每个候选，剔除夸大或歧义表达。输出候选、简短理由和唯一推荐标题，不修改正文。
```

User 模板：

```text
<reader_context>{{读者背景}}</reader_context>
<article>{{表达精修后的正文}}</article>
<packaging>{{本篇分发目标；未指定则留空}}</packaging>
<keywords>{{必要关键词；无则留空}}</keywords>
<title_length>{{项目配置的标题长度}}</title_length>
```

标题只在此阶段生成一次。程序把选定标题写回文章 H1；标题存在具体事实问题时定点修订。搜索关键词用于自然命名，不触发重新写正文。

**本版移除的任务**

| 原安排 | 新安排 |
|---|---|
| 独立大纲生成与大纲文件依赖 | 删除；P1 直接组织文章结构 |
| 每一步拼接全流程技能及重复规则 | 每步一份任务提示词，配合所需材料 |
| 初稿门禁、审稿、研判覆盖分别重复核验 | P2 集中审核事实、推理与简报核心命题 |
| 去 AI、风格门禁、风格返修 | P4 统一完成表达编辑 |
| 终稿只做字数提醒 | P3 超出范围时按已有事实和主线扩缩写，并对变动做局部复核 |
| 初稿后起标题，审稿后再起标题 | P5 正文完成后一次生成 |
| 固定的边界章节、建议清单、总结与互动 | 由内容决定是否需要 |
| 每步强调事实限制并整段重写正文 | P2 定位并修正实际问题；P3 只按字数调整篇幅 |
| 默认再增加独立发布前模型核对 | 不列为常规步骤；必要时复用原审稿任务核对变动 |

SEO、配图、排版属于按需的后续处理，不进入这份正文成稿主流程。现有程序对产物格式、未解决问题和发布状态的检查仍有其职责，不转化为给正文增加措辞要求的长提示词。

**示例：删掉冗余，保留实际含义**

以下例句为虚构表达示例，不作为文章事实，也不是每篇必须模仿的句型。

| 原文 | 精修目标 |
|---|---|
| 据某公司内部调查，受访团队每周节省两小时。这只是该公司内部口径，不代表所有团队。 | 据某公司内部调查，受访团队每周节省两小时。若调查局限会影响本文结论，应具体讨论该局限。 |
| 在指定测试环境中吞吐提升 20%。 | 保留这项测试条件，避免变成对所有环境的承诺。 |
| 多个段落反复列同一组缺失模块、硬件门槛，得出相同判断。 | 在合适位置讲清；后文用已有材料推进原因或影响。没有新内容就合并。 |

**实施与对比**

实施时删除大纲调用、输入依赖和阶段契约记录，接入 P1；再按 P2、P3、P4、P5 调整后续阶段。历史产物保留供对照，历史大纲不再作为新生成的必需输入。

验证使用相同的已确认简报、事实材料和模型，对比旧流程与本版直接成稿流程。重点看事实与逻辑是否成立、是否落实简报、是否适合目标读者、重复解释是否减少、阅读是否连贯；评价需引用具体段落，不按禁词数量打分。

### 已实施

- [运行时提示词](../../server/features/articles/application/article-prompts.mjs)：独立保存事实记录准备及 P1–P5；文章类型最多追加一条写法提示。
- [成稿执行器](../../server/features/articles/application/article-pipeline.mjs)：删除大纲调用、初稿质量审查、独立风格门禁、重复标题、SEO 全文改写、独立研判覆盖审查及重复发布前模型审查。审核事实与逻辑的职责统一交给 P2。
- [输入契约](../../server/features/articles/application/article-pipeline-contract.mjs)：保留主线、作者观点、确认的经历、采用与舍弃方向；事实记录保留对应证据、来源、时间和必要条件。
- [审核问题汇总](../../server/features/articles/application/article-review-issues.mjs)：读取本轮有效报告，避免历史失败结果继续阻塞重跑稿件。

### 运行细节

- 审稿有问题时默认修订一次，配置允许增加到最多两次；没有变化即停止。缺少关键材料时返回编辑处理并保留待审核状态，后续长度和表达阶段仍按各自职责执行。
- 审稿后检查字数。只有超出配置范围才调用长度调整；按调整量在结构调整和表达调整之间选择，最多执行两次并记录每次变化。长度调整和表达精修改动都只做差异复核，不由这两个阶段自动重写事实内容。
- 配图仅在明确指定需求时进入后续处理。默认不调用视觉规划或 SEO 全文重写。
- 手动重跑审核复用 P2，对当前保存的正文审核一次，附带程序格式和标题检查。
