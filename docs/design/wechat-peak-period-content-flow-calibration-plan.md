# 公众号高峰期内容生产链路校准方案

状态：核心链路已实施；离线历史样本回放与真实批次观察仍待执行<br>
日期：2026-10-26<br>
目标：依据已抓取的 6—7 月高流量内容特征，调整现有文章与 GitHub 贴图从采集、研判、选题到成稿的生产链。发布后反馈不属于本次实施范围。

## 1. 决策摘要

账号的两个内容方向保持不变：

- **文章**继续覆盖职场与科技技术热点。
- **贴图**继续推荐 GitHub 项目。

本次不是加一套事后复盘/画像系统，也不是因为高流量样本里出现国内大厂就把选题范围缩成“大厂新闻”。需要复用的是高峰内容所体现的读者价值机制：**事件或工具与目标读者的工作足够接近，读者能看见具体冲突、代价、选择或任务结果，正文/贴图能用证据兑现标题承诺。**

文章切口在**事实研判之后、现有选题总榜最终评分之前**形成：研判阶段先提取读者影响证据；现有 topic generation 和 `editorial-exploration` 围绕同一事件生成、比较具体角度；然后使用现有评分和文章选题总榜，由编辑锁定切口并进入文章生成。GitHub 项目贴图使用单独的项目任务/结果研判和故事板链。

```text
已抓取样本和实际发表格式
  → 文章模式 / 贴图模式及固定回放样本
  → 当前来源采集与事实研判补齐读者影响/工具任务证据
  → AI 提出切口种子并在 editorial-exploration 展开多角度
  → 沿用现有文章评分和选题总榜，强化具体读者利益的判断
  → 编辑锁定一个切口及证据
  → article-pipeline 生成文章；GitHub 项目经独立 storyboard 链生成贴图
  → 用历史高峰与普通样本离线回放检查链路
```

## 2. 样本证据与设计边界

所有样本格式以公众号后台“发表记录”为准。阅读、分享和关注只用来选取对照样本；不同内容格式分开比较。当前历史指标没有统一的发布后观察年龄，因此不能将历史阅读绝对值解释为内容机制的因果证明，也不能据此计算可靠的跨月转化率。

### 2.1 高峰文章：事件类别不等于有效切口

| 日期 | 后台格式 | 样本切口 | 阅读 |
|---|---|---|---:|
| 6/23 | 文章 | 美团产品协作冲突，“产品是传话太监” | 2,639 |
| 6/19 | 文章 | 钉钉 CEO 全员信/组织内部沟通 | 1,175 |
| 7/2 | 文章 | 字节办公设备与岗位风险，“借下电脑就能丢饭碗” | 2,008 |
| 6/30 | 文章 | 大厂内部信 | 829 |
| 6/24 | 文章 | AI 收费与免费模式变化 | 65 |

样本提示的候选机制：具体主体和行为、读者熟悉的工作场景、冲突/反常、明确的员工或开发者后果。AI 与科技事件仍是账号范围，但仅有产品发布、参数或行业声量时，若找不到具体读者影响，就不能仅凭题材热度声称切口贴近读者。

**国内大厂是样本背景，不是评分条件。** 评分对象是文章角度，而非事件所属公司的国别或知名度。AI 产品变化、开源技术和产业事件只要能由证据连接到岗位、协作、成本、效率、工具链或职业选择，就应在现有选题总榜中体现其具体读者利益；无法建立这种联系时，仍可按现有事件价值和账号契合参与排序。

### 2.2 高峰 GitHub 贴图：任务到结果，而非文章式热点评论

| 日期 | 后台格式 | 项目/包装机制 | 阅读 | 分享 | 阅读后关注 | 关注/千阅读 |
|---|---|---|---:|---:|---:|---:|
| 6/24 | 贴图 | 一条命令借鉴/复刻网站 | 5,265 | 705 | 132 | 25.1 |
| 6/26 | 贴图 | PDF 转 Markdown | 3,668 | 560 | 62 | 16.9 |
| 6/27 | 贴图 | 开发者免费服务/资源 | 4,210 | 505 | 60 | 14.3 |
| 7/1 | 贴图 | MCP 工具 | 4,302 | — | 43 | 10.0 |
| 7/10 | 贴图 | 知识图谱工具 | 7,372 | — | 66 | 9.0 |

贴图候选应回答：读者做什么任务、项目能产出什么可见结果、是否有可核验演示、如何上手、有哪些限制。阅读/分享和关注是不同价值信号；资源合集与高关注工具不能混为一类，也不能以文章的点击/冲突评分解释贴图表现。

近期贴图多数约 41—112 阅读，另有一条开发者分手梗约 557 阅读。轻松共鸣可以保留为探索项，但不替代 GitHub 工具推荐主线。

## 3. 当前架构与需要修正的断点

### 3.1 文章链

当前研判与选题主链大致为：

```text
research-pipeline
  → 事件归并、热度与事实研判
  → discussion-research-stage 的 topic_generation
       生成 candidate_title / core_question / angle / thesis_seed /
       target_reader / click_reason / reader_payoff / reader_entry_score
  → topic-candidate-generation 的核心8 + 黑马2 + 候补3预选
  → editorial-exploration brainstorm / synthesize
  → scoreCards 计算文章候选分并生成总榜
  → 编辑锁定 brief
  → article-pipeline 和写作技能成稿
```

代码位置：

- 研判和编排：`server/features/research/application/research-pipeline.mjs`
- AI 选题生成提示与解析：`server/features/research/application/research/discussion-research-stage.mjs`
- 预选逻辑：`server/features/research/domain/topic-candidate-generation.mjs`
- 切口脑暴/综合：`server/features/research/application/research/editorial-exploration.mjs`
- F 评分与总榜：`scoreCards()`、`markdownRanked()`，均在 `research-pipeline.mjs`
- 成稿：`server/features/articles/application/article-pipeline.mjs`、`skills/wechat-mp-topic-to-article/`

**关键断点：** 当前 AI 选题生成已有一个 `angle` 字段，但没有强制近期触发事实/来源及问题可回答性门禁；程序随后又在深入脑暴和 `scoreCards()` 前分配核心 8/黑马 2/候补 3。初始角度缺少时效或过于宽泛时，仍可能挤占最终名额。改造应在 topic generation 做 AI 语义资格判断并由程序校验必填和证据引用；通过门禁的候选再展开少量实质不同角度，最终 8+2+3 放到现有角度评分之后。不另建角度榜单或评分实体。

### 3.2 GitHub 贴图链

当前项目路线：

```text
collection-job-manager
  → planRepoDiscoveryQueries
  → GitHub 多场景搜索及兴趣过滤
  → 项目价值/社会贴图候选评分
  → social-card-routes
  → repository-card-storyboard
  → 页面内容、配套文案和贴图生成
```

主要位置：`server/features/collection/application/collection-job-manager.mjs`、`server/features/collection/llm/repo-discovery.mjs`、`prompts/collection/repo-discovery-queries.md`、`server/features/research/domain/social-scoring.mjs`、`server/platform/http/routes/social-card-routes.mjs`、`skills/repository-card-storyboard/`。

改造重点是把具体读者任务、预期输出、演示证据和上手限制前移到查询与项目核验，不把 GitHub 贴图并入文章榜，也不把文章模式用在故事板上。

GitHub 贴图的发布标题和配套文案需要落实同一任务—结果主线：标题先写读者要完成的任务/场景，再写可见结果，项目名主要承担识别作用；配文只展开一个主场景，保留 1–2 个关键亮点、必要的运行前提和一个清晰获取入口。避免把 README 的多场景、功能清单、兼容项、版本/许可、完整命令全部压进配文；不实测时明确标作文档整理。运行时规则登记在 `prompts/manifest.json`，正文存放于 `prompts/social-cards/copy*.md`，技能指南同步约束格式与信息取舍。默认以 180–320 个中文字符作为配文聚焦目标（不计标题、URL、标签），必要的运行条件与事实边界可以使文案稍长。

## 4. 切口识别的职责与时点

切口不是程序通过公司名、题材词或标题模式做的正则分类。它是 AI 基于研判证据提出并比较的编辑假设；程序负责 schema、来源和资格门禁；编辑负责锁定。

| 环节 | 负责什么 | 不负责什么 | 输出 |
|---|---|---|---|
| 事实采集/研判 | 确认主体、动作、场景、影响对象、直接后果、证据和未知项 | 不把事件直接包装成爆款标题，不凭空推断读者受影响 | 现有研判素材和事件候选字段 |
| topic generation | 从研判材料提出多个有证据差异的切口种子，指出读者是谁、为何关心、读完得到什么 | 不只把事件摘要改写成标题；不在此完成唯一排序 | 现有 topic candidate 字段 |
| editorial exploration | AI 围绕同一事实展开不同核心问题的角度，比较具体职场后果、决策传导和科技影响等路径；提供证据、反证、标题承诺和差异 | 不重做事实研判、不补造来源、不绕过编辑 | 现有 brainstorm card 字段 |
| 选题评分 | 使用现有 `reader_entry_score`、`readerStakeScore` 和 F 流程评分，在原有选题总榜中排序 | 不另建榜单或评分模型，不预测阅读量 | 现有 `scoreCards()` 结果和总榜 |
| 编辑锁题/成稿 | 编辑选择可写角度；成稿按已锁定 brief 执行并兑现承诺 | 不在文章初稿阶段重选题、不照搬历史标题或事实 | 已锁定 `ArticleBrief`、文章产物 |

因此，切口识别是**研判后的选题展开/脑暴阶段**；研判阶段准备证据并给出初始角度，脑暴负责展开和比较，之后沿用现有评分与总榜；成稿只消费已锁定切口。

## 5. 现有选题流程与评分的最小改造

### 5.1 不增加分类、榜单或评分实体

截图中的热点素材分类继续按现有六类题材和 GitHub 项目发现归类；本方案不替换这些分类，不新增“程序员身边事”或“AI/科技热点”榜单，也不新增独立的 `reader_proximity` 分数或候选数据对象。

“程序员身边事”描述的是某个文章切口与读者工作/生活的关联强度，不是事件题材。它通过现有文章候选里的读者入口、读者利益和文章化评分字段体现。原有 `topics-ranked.md`/文章选题总榜仍是唯一选题排序入口；AI/科技事件继续按原有题材、事件价值、账号契合和文章质量参与竞争。

### 5.2 复用并校准现有读者利益字段

现有 topic generation 已输出 `target_reader`、`click_reason`、`reader_payoff`、`reader_entry_score`；brainstorm card 和 `scoreCards()` 已有 `readerStakeScore`、`readerTarget`、`readerAction`、`readerConsequence`、`readerStakeEvidence` 等字段。改造优先修订这些字段的提示词解释、AI 评分 rubric 和报告展示，不新增平行 schema。

校准重点：

- `target_reader` 写具体角色和使用/工作场景，不写“所有职场人”“所有开发者”。
- `click_reason` 说明事件为什么与该角色现在有关，避免只重复热度或产品新鲜度。
- `reader_payoff` 写读者读完能判断、选择、避免或采取什么行动。
- `readerStake`/`readerConsequence` 必须描述具体后果，例如岗位、协作、成本、效率、工作流或职业选择的变化。
- `readerStakeEvidence` 和 candidate evidence refs 指向事实来源；无证据的影响写为未知或待核验，不给确定性高分。
- AI 负责语义判断和理由；程序校验必填项与来源引用并沿用现有分数计算。不能用“大厂”“AI”“裁员”“程序员”等关键词直接加分。

首轮只校准现有子项的定义和提示词，不直接改全局 F 公式权重。用历史回放确认高峰样本和普通样本的区分后，再评估是否需要调整已有 `readerStakeScore` 在 B 中的权重，避免一次改多个变量。

### 5.3 方案比较与选择

| 方案 | 改动方式 | 优点 | 风险/不足 | 决策 |
|---|---|---|---|---|
| A. 新增“身边事/AI科技”分类或平行榜单 | 扩展分类/榜单/查询界面和候选数据 | 可以单独展示 | 把读者关系误当题材；引入新数据结构和排序概念；与现有六类题材榜重复 | 不采用 |
| B. 全局提高 F 的读者利益权重 | 直接修改 `scoreCards()` 公式 | 只保留一个列表 | 影响所有文章类别，可能压低宏观 AI/科技趋势；难判断是提示词还是权重造成变化 | 暂不采用 |
| C. 校准现有读者字段，修正预筛时点，沿用现有总榜 | 扩展现有角度生成，校准 `reader_entry_score`/`readerStakeScore` 语义；brainstorm 后再做最终筛选 | 改动集中；不增加概念；保留热点分类和 AI/科技选题空间；可用离线回放验证 | 需要调整当前预筛顺序并控制模型候选数量 | **推荐** |

### 5.4 预筛顺序调整

当前核心 8/黑马 2/候补 3 的预选发生在深入脑暴和 `scoreCards()` 之前，且时效性与问题范围没有成为候选资格门禁。调整为：

1. 对全批事件沿用 `eventHeatRanking` 轻量筛查后进入现有配置的 Top-K 深研范围；该热度值已综合读者关联、读者影响、信息增量、证据质量和新鲜度，不新增分类/榜单。冲突及反常由后续研判确认；之后运行 topic generation，AI 必须给每条候选标注近期事实触发点、对应来源、问题是否可由研判证据回答；无当前触发事实、泛问题或证据不足的候选标记为未覆盖，不进入脑暴；
2. 程序校验门禁字段、事件 ID、来源 ID、研判依据和现有候选结构，不用关键词规则识别语义上的“新”或“宽泛”；
3. 将所有通过资格门禁且有研判依据的候选送入 `editorial-exploration` 展开角度并输出读者利益、事实支撑、反证和包装；模型发现候选与事实矛盾或无法回答时返回 `NO_ANGLE`；
4. 对有效脑暴卡运行现有 `scoreCards()`；仅在此后按 F、文章资格、写作状态和现有读者入口要求分配核心/黑马/候补名额；
5. 总榜保留完整可审阅结果，最终文章候选池只接收评分后确定的名额，并记录未入选/未填满原因。

候选总量沿用 topic generation 的现有上限；不新增榜单或评分。文章资格、来源事实和风险门禁不放松。时效性和“具体问题可回答”成为漏斗资格，不再由初稿/审稿替代选题。
## 6. 两条内容生产链的调整

### 6.1 长文：在现有文章选题链中展开和比较切口

```text
现有热点来源与事件归并
  → 现有事实/讨论研判：补齐主体、动作、影响对象、后果、证据和未知项
  → topic_generation：核验近期触发事实、来源和问题可回答性；不合格候选不进入脑暴
  → editorial-exploration：展开具体角度、读者利益/证据/反证；无法兑现则 NO_ANGLE
  → 沿用现有文章评分字段和 F
  → 评分后在现有总榜中筛核心/黑马/候补
  → 编辑锁定 brief
  → article-pipeline 生成文章
```

**采集和研判：** 保持现有职场/科技来源与热点范围；沿用覆盖全批事件的现有 `eventHeatRanking` 子项（读者关联、读者影响、信息增量、证据质量、新鲜度）排序，按已有 Top-K 配置挑选深研事件，不增加平行榜。深研提示抽取主体、行动/决定、发生场景、具体影响对象、岗位/协作/效率/成本/工作流/选择后果、来源证据、反证和未知项。没有读者影响证据时保留为普通热点候选，不强行包装成职场冲突。

**切口生成：** `topic_generation` 在现有候选字段上增加时效资格字段（`timeliness_status`、`freshness_basis`、`freshness_source_ids`）和可回答性字段（`answerability_status`、`answerability_basis`）。同一事件/关系先保留一条最有证据、最可回答的候选，不以标题换词凑数；脑暴可比较不同解释路径，再将具体角度写入探索卡。只有 `current + answerable` 且触发事实可回指来源的候选才进入脑暴；“旧事件只有新网页”“长期趋势”“谁怎么看”等泛问题不通过。AI 做语义判定，程序验证枚举、必填值、事件与来源 ID；程序不以正则推断语义新旧或宽泛。脑暴继承这些资格依据，仍可对材料冲突/问题不可答的候选返回 `NO_ANGLE`。

重点比较的角度路径：

- 具体员工/开发者工作场景中的冲突、代价或选择；
- 公司或产品决策如何传导到团队、岗位、协作或责任；
- AI/科技变化对工作流、效率、成本或职业选择的影响；
- 证据只支持宏观趋势时，保留宏观技术角度，不硬造个人经历。

**评分与预筛：** 不新增榜单或分数。沿用现有 `reader_entry_score`、`readerStakeScore`、`readerTarget`、`readerAction`、`readerConsequence`、`readerStakeEvidence` 和 F。初筛仅执行时效、可回答性、研判依据等资格门禁，不提前分配核心/黑马/候补；脑暴和 `scoreCards()` 完成后，才按既有文章资格、写作状态、读者入口和 F 竞争分配 8/2/3 名额，并写回原有文章总榜。

**成稿：** 编辑锁定角度后，`article-pipeline` 与 `wechat-mp-topic-to-article` 写作技能按已确认简报写作。简报携带选题漏斗确认的近期触发事实、时间与来源、读者后果、事实与反证。初稿沿用锁定问题，不重新判断是否值得写、不扩成宽泛趋势；审稿检查是否忠实兑现锁定问题、读者影响和证据，不另做时效选题筛选或替代编辑重新选题。

### 6.2 GitHub 贴图：在现有仓库发现和故事板链中强化任务结果

```text
现有 GitHub 场景查询组
  → 项目搜索、去重与事实核验
  → 补齐读者任务、预期输出、演示证据、上手成本和限制
  → 沿用项目评分与贴图候选流程
  → 编辑锁定项目和展示主线
  → repository-card-storyboard
  → 逐页内容、配套文案、排版与门禁
```

查询继续覆盖网页/UI、文档处理、开发者免费资源、MCP/工作流、AI 编码/设计、远程开发/预览等现有场景；优化现有查询 prompt，让查询结果更偏向可展示的读者任务，而不是新增采集系统。候选和故事板沿用现有结构，补充或明确以下信息：

- `reader_task`：读者要完成的具体工作；
- `expected_output`：项目能生成或改变的可见结果；
- `demo_evidence`：截图、演示、示例输入输出或可信文档；
- `setup_friction`：安装、账号、依赖、部署与权限成本；
- `limitations`：适用边界、功能限制和维护状态。

先过项目真实可用、读者价值和证据门槛，再评估是否适合做卡片。故事板封面承诺结果，内页展示问题、能力、演示、快速上手和限制。没有证据就降级包装，不补造亲测或演示结果。

## 7. 实施阶段与交付

阶段沿现有生产链的依赖顺序推进。本次交付终点是采集—研判—角度展开—成稿链通过历史样本离线回放；发布后反馈不在本次阶段内。

### 阶段 1：整理历史样本与可复用范例

**涉及模块：** 内容索引/发表记录映射、现有文章和贴图提示词/技能。<br>
**改法：** 按公众号发表记录确认文章与贴图格式；分别选取高峰样本和同格式普通样本，整理其切口/任务结果、可用正文/脚本、支持证据和限制。把验证过的结构范例补入现有 prompt/skill，不新建画像服务或独立配置体系。<br>
**交付：** 文章与贴图两组可追溯范例及现有技能提示词更新清单。<br>
**验收：** 格式与发表记录一致；只有标题/指标的样本不当作已分析正文；每条提示规则能回指具体样本和证据。

### 阶段 2：调整采集和事实研判

**涉及模块：** `discussion-research-stage.mjs`、现有研究候选字段；`collection-job-manager.mjs`、`repo-discovery.mjs`、GitHub 查询 prompt。<br>
**改法：** 文章热点范围不变，研判要求补充具体读者影响及证据；GitHub 查询前置任务、结果、演示、上手和限制信息。<br>
**交付：** 现有候选对象包含切口所需的读者影响或项目任务结果信息。<br>
**验收：** 有高峰内容机制的历史样本能补齐所需证据；一般 AI/科技热点仍可作为普通文章候选；无证据处明确标缺口。

### 阶段 3：调整切口生成、评分口径和预筛顺序

**涉及模块：** `topic-candidate-generation.mjs`、`research-pipeline.mjs`、`editorial-exploration.mjs`、`scoreCards()`。<br>
**改法：** topic generation 与 editorial exploration 都在现有结构内生成/比较多个真实不同的切口；校准现有读者入口和读者利益分项，不新增榜单/评分模型；将最终核心/黑马/候补筛选移到角度展开和评分之后，同时保留来源、文章资格、风险、重复硬门禁。<br>
**交付：** 现有文章选题总榜中出现更可比较的角度和更具体的读者利益理由。<br>
**验收：** 高峰文章能从事实中展开相似的机制；普通候选能说明缺少什么证据/读者利益；选题范围没有被“大厂”或“AI”关键词限制。

### 阶段 4：改进文章和贴图生成提示

**涉及模块：** `article-pipeline.mjs`、文章提示词、`wechat-mp-topic-to-article` 写作技能；`social-card-routes.mjs`、`repository-card-storyboard`。<br>
**改法：** 文章候选在 topic generation 通过近期触发事实、来源和可回答性门禁后才进入脑暴；初稿和审稿严格遵循已锁定 brief，缺事实时报告具体材料缺口，不重新承担选题资格判定。贴图故事板将任务结果模式和当前仓库事实传入既有页面生成阶段。文章和贴图分别执行内容兑现检查，不跨格式复用评分和范例。<br>
**交付：** 按既有产物流程生成的文章稿件与贴图故事板/配套文案。<br>
**验收：** 文章具体时效触发、读者后果、证据与标题承诺一致；贴图结果/演示/上手/限制有依据；没有未证实的亲测效果。

### 阶段 5：固定历史样本离线回放

**涉及模块：** 现有研究/写作管线、回放驱动或人工审阅清单。<br>
**改法：** 用固定高峰文章/贴图和同格式普通样本重跑采集/研判/角度/成稿；保存现有阶段产物和模型调用记录，逐项检查高峰机制是否被重新识别、普通候选是否被过拟合。失败项回到阶段 2—4 修订。回放不发布内容，也不改写历史指标。<br>
**交付：** 可审阅的样本映射、阶段产物、误入/漏入原因和修订记录。<br>
**验收：** 编辑能定位问题发生在采集、研判、切口、评分或生成环节；回放通过仅代表流程能表达目标机制，不承诺复刻历史阅读量。

## 8. 非目标与完成标准

本次不做：

- 新增“程序员身边事”或“AI/科技热点”榜单/分类；
- 改动截图所示的六类热点素材分类或 GitHub 项目发现分类；
- 新增独立 proximity 分数、榜单排序模型、画像数据库或 AI 自动学习服务；
- 发布后自动采集 7/30 日同龄期数据或据此自动调分；
- 将贴图阅读/关注表现用于文章评分，或把文章标题结构分用于 GitHub 卡片排序；
- 因大厂样本表现好而把公司类型固化成硬加分。

全部满足以下条件才算完成本方案：

1. 历史文章/贴图样本的格式与实际发表记录一致，案例与证据可追溯。
2. 文章研判输出具体读者影响及证据；GitHub 查询输出任务、结果、演示和上手限制。
3. 切口在研判后、成稿前由 AI 展开并比较；现有最终筛选不再早于深入角度展开。
4. 现有文章总榜使用校准后的读者入口/利益理由；热点素材分类保持不变。
5. 文章和贴图分别使用各自的生成流程与证据门禁。
6. 固定高峰/普通样本回放完成，重要误入/漏入可定位到采集、研判、筛选或生成环节。

发布后数据反馈属于后续校准工作，不是本次采集、研判或成稿改造的前置条件。

## 9. 架构依据

- 历史内容按真实发表格式分组，并对同格式高/普通样本做对照，避免把文章和贴图的指标或包装方式混为一谈。官方创作者分析也建议比较相同格式内容，并观察高表现与低表现内容的差异。[YouTube Analytics tips](https://support.google.com/youtube/answer/11912632?co=YOUTUBE._YTVideoType%3Ddesktop)
- 本方案沿用当前热点分类、候选数据、文章评分总榜、GitHub 项目发现和技能化成稿能力，只校准现有字段与阶段顺序，不另建一套榜单或反馈驱动系统。
