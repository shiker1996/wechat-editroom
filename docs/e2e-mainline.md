# 主链路端到端功能测试

## 运行

```bash
npm run test:e2e
```

测试位于 `test/e2e/mainline.test.mjs`，每次运行都会创建临时工作区和临时 SQLite 数据库，结束后清理，不会污染项目的 `data/`、`articles/` 或 `social-cards/`。

## 覆盖范围

测试启动真实 `server.mjs`，通过真实 HTTP API 验证：

1. 固定 RSSHub 来源能被采集并写入批次热点。
2. 采集返回的真实热点能通过候选接口进入文章和图文两条下游链路。
3. 真实执行打标、事件卡、单事件研判、脑暴和综合复排，并检查研判产物。
4. 研判生成的文章候选能完成文章流水线，并产生最终文章产物。
5. 仓库图文候选会通过真实仓库核验接口生成事实基座，再完成故事板、HTML 和布局审计，并产生 `my-design.html` 与 `card-plan.json`。
6. 任务失败会通过 `/api/jobs/:id` 暴露，测试不会只看 HTTP 202 就判定成功。

## 第二阶段验收点

主链路测试的固定性由四部分组成：

1. RSSHub 由本地固定 RSS 夹具提供，发布时间、条目 ID、标题和 URL 都是确定值；测试还会断言真实采集请求命中了固定路由。
2. 模型由本地 Replay 夹具提供，不访问公网或真实 API；每次请求都会记录命中的 Replay 类型，文章和图文故事板必须分别命中对应契约。
3. 数据库、配置、缓存和产物都位于每次运行新建的临时工作区；测试会检查 SQLite 文件确实创建在隔离路径中。
4. 采集、文章和图文任务都通过 `/api/jobs/:id` 轮询，只有明确进入 `completed` 才算成功；`failed`、`interrupted`、`cancelled` 和超时都会让测试失败。

采集前只创建批次、来源和运行配置，不预置热点、候选或文章源缓存。采集完成后，测试从批次 API 读取本次 RSS 返回的热点，再通过候选 API 创建下游候选；文章原文也通过真实备料接口从采集摘要生成缓存。这样可以验证“采集结果确实驱动了后续产物”，而不是只验证一组预置数据能否被流水线消费。

采集后的文章路线会继续经过真实的打标、事件卡、研判、脑暴和综合复排任务；测试从研判产物和候选接口读取文章候选，再进入编辑底稿和文章流水线。模型输出由本地 Replay 提供确定性结果，并对每个阶段检查命中的 Replay 类型。图文候选不再直接写入仓库事实表或 `fact-sheet.md`；测试启动本地 GitHub REST Fixture，通过可配置的 API 基地址让真实仓库分析器读取仓库元数据、README、License 和 Release，再由服务端保存事实基座和 Markdown 产物。

## 第三阶段验收点

主链路不再只检查任务状态和少数文件，而是按最终交付契约检查：

1. 文章链路必须生成简报、事实基座、大纲、各阶段稿件、SEO、终稿、视觉规划和发布合规等关键产物；产物必须归属于当前候选、文件存在且非空。
2. 文章终稿必须有 H1、H2、可见正文，并与 `/api/batches/:id/documents` 返回的 finalized 文档一致。
3. 图文链路必须生成事实清单、故事板、文案、HTML、布局报告和交付报告；故事板至少有封面与收尾页，卡片数量与页数一致。
4. 图文交付接口必须报告 ready，交付门禁必须通过，布局报告覆盖全部页面且不包含 overflow、clipped 或 horizontal overflow。

## 第四阶段验收点

在同一个隔离批次完成 API 主链路后，测试会用 Puppeteer 驱动一次真实图文用户流：打开工具图文、选择图文候选、点击“分析仓库”、点击“生成故事板”、点击“程序化生成”，并等待页面上的交付面板出现图片数量。随后再打开九个关键页面：工作台总览、热点全景、文章选题池、热点事件创作、文章编辑器、工具图文、产物中心、任务日志和采集源。每个页面都必须激活正确视图、页面有实际内容或明确空态、关键 DOM 区域存在；浏览器控制台异常、页面运行时异常、脚本/样式/API 等关键资源加载失败和服务端错误都会使测试失败。浏览器默认请求的 `favicon.ico` 不属于业务资源，单独排除。

RSSHub 和模型服务是本地固定夹具，不依赖公网或真实 API Key；业务服务、采集器、任务管理器、流水线和浏览器渲染仍然是真实实现。模型夹具只返回满足各阶段契约的确定性结果，因此它验证的是功能闭环和产物完整性，不验证模型内容质量。

## 第五阶段验收点

第五阶段把测试失败变成可定位的 CI 信号：

1. CI 在全量测试前单独执行 `npm run test:e2e`，主链路失败会直接阻断合并。
2. CI 设置 `E2E_ARTIFACT_DIR=test-results/e2e`；失败时保留临时工作区中的服务日志、RSS 请求、模型请求、失败堆栈和浏览器截图，并上传 14 天。
3. 异常矩阵固定覆盖任务 `failed`、轮询超时、RSS HTTP 503、模型 HTTP 502 和模型非法 JSON；这些情况不能被误判成成功。
4. 异常夹具仍运行在本地进程，不访问公网，也不写入项目正式数据库和产物目录。

## 第六阶段验收点

第六阶段把异常矩阵接到真实业务服务：

1. RSSHub 返回 HTTP 503 时，真实采集任务必须进入 `failed`，批次进入 `blocked`，并保留失败原因。
2. 模型服务返回 HTTP 502 时，真实文章 AI 任务必须进入 `failed`，不能产生 `09-FINAL.md` 的完成态。
3. 异常场景通过真实工作台 HTTP API 启动和轮询，测试夹具只替换上游依赖，不绕过采集器、任务管理器、模型网关或产物索引器。

## 改动后的使用建议

把 `npm run test:e2e` 放在合并前门禁；日常快速开发继续使用 `npm run test:fast`。新增主链路阶段时，优先在这个测试中增加一个可观察的最终产物或任务状态断言，避免测试只覆盖“接口被调用”。
