# 工具图文配套文案规则

只负责已锁定工具故事板的对外文案，不重新设计页序、页面职责或内容块。

## 输出形态

纯文本，直接可发布：不使用 Markdown 或 HTML 标记（标题、加粗、列表符号、链接语法一律禁止），结构只用分行、空行和数字编号表达；公众号与小红书图文均不渲染标记文案。

## 表达目标

- 先用一句话落到一个开发者具体任务/阻碍，再说工具把什么输入变成什么可见结果；读者价值优先于技术栈和项目沿革。
- 只挑 1–2 个最能解释主任务结果的亮点，最多补充一个关键前提或限制。不要将 README 全量改写成笔记：多个应用场景、所有功能、兼容库清单、版本/许可状态、完整命令和建议步骤不能同时堆进配文。
- 默认 180–320 个中文字符，不计标题、URL 和话题标签；为交代必要安装条件或未实测边界可适度超出，但先删次要背景与功能。
- 工具配文按“任务/痛点 → 项目提供的结果 → 1–2 个关键理由 → 必要前提/未实测边界 → GitHub 仓库主页”组织。只保留仓库主页，不另附 Releases/下载链接。每段只推进一件事。
- 对程序员说人话，但保留必要术语。
- 区分项目自述、第三方评价和作者判断。
- 没有真实体验时不用“我用了”“亲测”“踩坑”。
- 数字、免费、开源、性能、价格和节省时间必须有事实基座支持。

## 渠道

- 公众号：信息密度优先，短段落；末尾给 6–8 个准确话题标签。
- 小红书：可以使用克制的 emoji 和口语表达，末尾给 6–8 个准确话题标签。

## 事实边界

- Star、版本等实时数字必须保留采集时间语境。
- 开源协议、安装命令、权限和网络要求只采用已核验材料。
- 项目处于 alpha、beta 或实验阶段时必须明确说明。
- 未实际运行时保留“基于项目文档整理，未实际运行”。
