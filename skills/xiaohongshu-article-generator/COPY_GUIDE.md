# GitHub 工具贴图文案规范

适用于已锁定 GitHub 工具故事板的发布文案。文案解释读者任务、工具提供的结果、开始方式和限制；不重新设计故事板，也不虚构作者体验。

## 输出形态

纯文本，直接可发布；不使用 Markdown 或 HTML 标记。段落短而清楚，不暴露分页编号，不强行加入 CTA。渠道要求由运行时规则补充。

## 内容顺序

1. **读者任务/痛点**：第一段从一个具体开发任务或工作场景进入，写清卡在哪里、读者想拿到什么结果。优先选项目最能解决的一个场景；不泛称“提升效率”，也不编造读者普遍遇到的痛点。
2. **工具结果**：紧接着说项目把什么输入变成什么可见结果，以及它的主要实现路径。把“这个项目是什么”放在服务任务的位置，不用技术栈介绍代替读者价值。
3. **核心亮点**：只保留 1–2 个最能解释任务结果的差异点。最多可加一个关键限制或上手前提。不要把 README 的功能、适用场景、兼容库、版本、协议、所有命令逐项搬进配文；次要信息留给卡片页面或项目文档。
4. **获取地址**：独立成行，只给 GitHub 仓库主页，不再附加 Releases/下载链接。仓库主页中已有安装与版本说明；准确标注为“项目主页”，不要称为安装包直链。没有地址素材时标注待补，不猜 URL。
5. 需要话题标签时，使用与项目和任务直接相关的词，不用宽泛种草词凑数。

工具推荐配文默认控制在 180–320 个中文字符（不计标题、URL 和标签）；这是压缩信息的目标，不是截断事实的硬上限。运行前提、关键风险或未实测声明必需时可以稍长，但应删掉次要功能和背景介绍。

## 表达和证据

- 面向程序员说清楚“输入—处理—输出”，保留理解任务所需的技术术语。
- 区分仓库文档陈述、第三方信息和作者实际验证；来源归属不得混淆。
- 没有真实体验记录时，不写“我用了、亲测、实测、踩坑”。
- 免费、开源、性能、价格、兼容性、离线能力和节省时间都需要对应来源支持。
- Star、版本等会变化的数字带采集时间；它们不代替工具用途或质量判断。
- 不采用“神器、封神、天花板、闭眼冲”等空泛评价，也不编造效果数字和比较结论。
- 项目处于 alpha、beta、实验阶段，或运行条件尚未核验时，明确写出边界。
- 仓库主页、Release 页面和可直接下载的安装包是不同入口，按事实基座提供的地址准确标注类型。

## 发布前检查

逐句检查事实基座是否有来源；确认开头的任务和结果与标题、封面及故事板一致；确认正文没有超出项目材料的效果承诺、运行结论或体验描述。发现证据缺口时，改成有边界的项目文档描述，或删除该句。发布前做一次“README 摘要检查”：若配文同时介绍多个不相干场景、超过两个功能亮点，或连续堆列版本/许可/适配器/完整安装步骤，保留能解释主任务结果的内容，其余删去或移到卡片页。
