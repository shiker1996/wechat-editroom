# GitHub 工具贴图标题规范

适用于 GitHub 开源工具推荐贴图。标题的工作是让目标读者迅速判断“这能帮我完成什么”，不预测阅读量，也不靠情绪词或 Star 数替代用途。

## 标题信息顺序

1. 优先写具体任务、输入或读者场景。
2. 接着写工具可产生的可见结果，或它解决的明确阻碍。
3. 项目名用于识别，可放标题后半句或封面副标题。
4. 只保留事实基座中有证据支持的信息；标题承诺必须由故事板后续页面解释、展示或注明边界。

可用表达结构：

- `把什么输入变成什么结果`：例如“把 PDF 转成可检索的 Markdown”。
- `在什么场景完成什么任务`：例如“从网页截图生成可预览页面”。
- `什么问题可以如何处理`：例如“代码库太大？先生成可检索的结构图”。

这些是结构示例，不是对任意仓库的功能声明。实际标题只能根据该项目的事实基座生成。

## 证据要求

- “免费”需要价格或许可信息支持；“开源”需要确认许可状态。
- “离线/本地”需要项目文档明确说明运行方式和网络依赖。
- “一键/一条命令/无需配置”需要完整使用路径或运行记录支持。
- “几分钟”“节省时间”“提升效率”“更快/更省”等效果需要对应测量或可比证据。
- “亲测/实测”只能用于当前素材明确提供的实际运行记录。
- Star、排名、榜单和发布时间只能作为带时间语境的辅助事实，不代表质量或读者价值。

## 不采用的写法

- 用“神器、封神、天花板、闭眼冲”等评价词代替任务和结果。
- 只写项目名、技术名词或“程序员必备”，不说明读者能做什么。
- 为满足字数而强行添加数字、痛点、情绪词、行动号召或无依据对比。
- 先许诺结果，正文却没有对应证据、步骤或限制说明。

## 生成与检查

先从事实基座抽取“读者任务—输入—项目能力—可见输出—证据来源—限制”，再生成一个可发布标题。检查标题中的每个结果词是否能映射到故事板页面和来源；映射不到就改弱或删除。标题长度服从信息清晰和渠道要求，不设置无数据依据的统一字数门槛。
